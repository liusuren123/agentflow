| 标记 | 含义 | 处理方式 |
| --- | --- | --- |
| `[评审·Critical]` | 会导致迁移失败、数据损坏或协议不可用 | **开工前必须裁决** |

## 5. 五个必修项（如果只改五处，改这五处）

### 5.1 [Critical] 端口顺序就是存盘契约，必须冻结为 append-only

- **问题**：已存盘的 edge 用的是**端口数组下标**（`{id, fn, fp, tn, tp}`，`fp`/`tp` 是数字索引），而索引由 `node.json` 里 `ports[]` 的数组顺序决定。文档只写了「聚合层建立稳定 id → 索引映射」，没写这个顺序以后能不能动。
- **后果**：中间插入端口 → 存量工作流的边**静默错位**；删除端口 → 越界后引擎回退到 `src.value`，行为静默改变。存量数据（localStorage + SQLite）**无版本号、无 schema 校验、无迁移钩子**，无法识别「这条边是顺序变更前存的」。而且 `addEdge` 有 3 个调用点，其中自动连线用「首个兼容端口」，顺序变化连**新建连线**的落点都会变。
- **要写的**：端口数组 append-only；删除端口 = major + ADR + 迁移脚本（无法映射的边显式报「连线失效」，禁止静默丢弃）；工作流文档 `schemaVersion` 单独立项。
- **证据**：`apps/web/src/legacy/app.js:1295`、`:1530-1531`、`:1719/1722`、`apps/server/src/engine.ts:74`、`:92-93`、`apps/server/src/store.ts:149-183`

### 5.2 [Critical] `app.js:2048` 运行期回写注册表，且现有验收机制在原理上覆盖不到

- **问题**：前端 `app.js:133` 的 `DEFS = NODES` 是**同一对象引用**；`:2048` 在探测到后端后执行 `DEFS.llm.params[0].o = prov.models.map(...)`，即**运行时改写 `packages/shared` 的导出对象**，同时耦合三样东西：节点 type 字面量 `llm`、`params` **数组下标 `[0]`**、旧字段键 `.o`。目录化后改键名 / 改顺序 / 冻结对象，任一项都会导致白屏或静默写错参数。
- **为什么单列**：它在 `dev:web`（vite 代理 `/api`）与生产 `npm start` 下**真实执行**（`app.js:2414` 启动时主动调用），但三道闸门都测不到——gate 是纯静态服务（`/api/health` 必然 404，分支永不进入）、契约测试在 Node 侧不跑 DOM、smoke 只打后端 API。
- **要写的**：目录化后 `NODES.llm.params` 的顺序与键名逐字不变；聚合层导出不得 `Object.freeze`（或明确该字段运行期可写）；验收补**在线态人工 E2E**（起后端 + 打开 LLM 属性面板，确认下拉有值、无 TypeError）。
- **证据**：`apps/web/src/legacy/app.js:133`、`:739`、`:2048`、`:2411-2414`、`apps/web/vite.config.ts:9`、`tools/pixel-gate/gate.mjs:32-41/69`

### 5.3 [Critical] §4.2 的映射表是单向的，缺「反向合成」规则（`caps` 顺序会直接撞像素门禁）

- **问题**：表只写「旧 → 新」，而实现轮真正要做的是「`node.json` → 现行 `NODES` 形状」。两个必踩点：① 新协议写 `skills`（复数）、旧值是 **`'skill'` 单数**；② `caps` 数组**顺序**决定能力 chip 的渲染顺序，`['mcp','skill']` 写反就是「Skill MCP」，在 0 容差像素比对下直接红。
- **要写的**：反向合成小节；`caps` 固定输出 `['mcp','skill']`（禁止按 `Object.keys` 枚举）；契约测试补 `assert.deepEqual(NODES.llm.caps, ['mcp','skill'])`。
- **证据**：`apps/web/src/legacy/app.js:334`、`:968-997`、`packages/shared/src/nodes.ts:25/58`

### 5.4 [Critical] 加载机制「留给实现轮」不可接受——三种方案在现有配置下全有硬阻塞

- **问题**：§3 说加载方式「迁移实现定」，但这不是选型偏好：
  - 「构建期 `fs.readdir` 扫描」：`packages/shared` 只导出 `dist`、`build` 仅 `tsc` 不复制 JSON → `npm test` / `npm start` 直接崩；
  - `with { type: "json" }`：`tsconfig.base.json` 未开 `resolveJsonModule`，改它会牵动 web / server 两个 workspace；
  - 运行时扫描：前端 `viteSingleFile` 单文件产物 + 浏览器无 `fs`，不可行。
- **要写的**：定死「显式静态 JSON import + 开启 `resolveJsonModule`」，并用契约测试断言「`nodes/` 目录数 = NODES 键数」防漏 import；另需评估聚合层是否突破 AGENTS.md 的 400 行上限。
- **证据**：`packages/shared/package.json`、`packages/shared/tsconfig.json`、`tsconfig.base.json`、`apps/web/vite.config.ts`、`packages/shared/test/contract.test.mjs:8`

### 5.5 [Major] `params[].k → id` 是文档自造的陷阱：后端硬编码 34 行 / 37 处 / 23 个键

- **问题**：`id` 在本文档里有**两种相反含义**——端口那节是 `inputs[].n → label` 并**新增** `id`（稳定标识）；参数这节 `k → id` 只是**原键改名**（没有任何新增）。读者按端口节的惯性，很容易以为可以给参数 `id` 顺手取个好读的名字，而这会打穿后端硬编码。
- **为什么无守卫**：`defs-drift.test.mjs` 只比对参数**键集**与默认值，**不验证 handler 里的 `p.xxx` 是否与注册表一致**。改名后：键集自洽（绿）、默认值一一对应（绿）、handler 全读到 `undefined`（运行时静默全线失效）。
- **要写的**：`params[].id` 必须逐字等于现行 `k`；同一键名跨节点可异义（`p.to` 在 http=超时 / notify=接收人 / approval=超时策略），改名须全仓同步、禁止按节点「优化命名」；补一条「参数键名 ↔ handler 引用一致性」机械守卫测试。
- **证据**：`apps/server/src/handlers.ts`（29 行 / 32 处）、`apps/server/src/llm.ts:15/34/35/36`、`apps/server/src/engine.ts:128`；`packages/shared/test/defs-drift.test.mjs:31-58`

## 6. 两个超出预期的发现（建议单独看）

### 6.1 33 个参数里有 5 个是「僵尸参数」——而契约测试把它们锁进了基线

`trigger.mode` / `trigger.cron` / `trigger.path` / `userinput.vtype` / `userinput.req` **没有任何代码读取**。铁证：`handlers.ts:18-20` 的签名是 `async trigger(ctx)`，**根本不取参数对象**，`out` 里的「手动触发」是硬编码字面量——把 `mode` 切成「定时触发」，运行日志照样显示「手动触发」。

问题在于：`defs-drift` 断言「参数总数恰为 33」，把这 5 个一起锁进基线；§6.2 又用 `visibleIf` 把 `cron` / `path` 的显隐正式化。于是迁移后它们被完整保留、测试全绿、文档有据可查，**却依然什么都不做**——这不是防止漂移，是把漂移固化成契约。

**建议**：协议加 `params[].implemented`（缺省 `true`，这 5 个标 `false`），§7.2 的「协议不虚构能力」升格为「**协议不虚构行为**」并覆盖 `params`；验收的「33」拆成「33 个已定义 + 28 个已实现」两个数。迁移内**不要**删除这 5 个参数（触 UI），只在 README「现状备注」标注「UI-only，后端未接入」。

### 6.2 「节点知识」散落 8 处，只有 1 处有自动化保护

| 侧 | 位置 | 内容 | 危险点 |
| --- | --- | --- | --- |
| 前端 | `app.js:2048` | 运行期写 `DEFS.llm.params[0].o` | type 键 + 下标 + 旧键三重耦合 |

| 前端 | `app.js:1859-1876` | `RUN_META`（16 键） | `\|\|{dur:600,out:()=>'完成'}` **静默回退** |
| 前端 | `app.js:103-114` | `MCP_SERVERS` | 与 DEFS `caps` 无契约关联 |
| 后端 | `engine.ts:128` | `n.type==='condition'` + `p.expr` | type 与参数键双硬编码，`cond` 事件唯一发射点 |

## 8. 值得保留的设计（不要在这些地方提改进意见）

为避免下一位评审人重复质疑，以下是**经核查成立、建议保留**的决定：

1. **把 BK-0021 定性为「存储形式重组、内容零漂移」**——给「是否触需批准区」留了唯一判据（内容是否漂移），比主观判断可靠。
2. **主动声明「本规范不构成豁免」**——协议文档最容易自我授权，这里显式否定并指向 POLICY 需批准区（`docs/evolution/POLICY.md:23` 确有该条），是文档层面的权限谦抑。
3. **`edge` 存盘格式不动、内部改用稳定 id**——外兼容内改进，避免了动存量 localStorage / SQLite / 引擎取值路径。
4. **把连线规则从 `app.js` 里挖出来并挂精确行号**——行号经核查属实（`typeOk` 在 `:43`），让「改连线规则」从改代码变成改数据。
5. **「定义文件无 import、无函数字面量」**——这是目录制能同时被 Vite / tsc / `node --test` 三套工具链消费的技术前提。
6. **HANDLERS ⊇ NODES 提升为协议契约**——有既有测试背书（`handlers-coverage.test.mjs` 三条约束），不是凭空发明。
7. **能力 → 护栏的绑定表**——`net → guard.ts`、`fs → sandbox/`、`exec → 子进程+超时` 与 `AGENTS.md:51-52` 逐字对应，把「能力声明」从描述变成带义务的承诺。
8. **闭枚举 + 新增走修宪**——在 0 容差像素门禁的仓库里，开放枚举会让「新增一个 widget」悄悄滑过 UI 审查。
